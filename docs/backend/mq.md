## 为什么需要消息队列

1. 解耦: 减少直接依赖
2. 异步: 缩短主流程响应时间
3. 削峰填谷: 缓冲突发流量

消息队列使用的设计模式

- 观察者模式
- 发布订阅模式

## Kafka

- topic: record 消息按 topic 主题分类, producer 生产者向指定 topic 生产消息, consumer 消费者从指定 topic 消费消息; topic 支持多订阅, 同一个 topic 可以被多个消费组消费
- partition: topic 拆为多个 partition 分区, 每个分区是一份追加 (append-only) 日志, 分区内的消息有 offset 偏移量, 分区是分布式日志的基本单位, 也是并行读写的基本单位
- broker: kafka 集群中的服务进程节点, 负责接收生产者写入请求, 持久化分区日志, 响应消费者拉取请求, 维护副本同步状态; 一个 broker 可以承载不同 topic, 不同分区的副本 (leader 副本或 follower 副本), 一个分区的多个副本尽量分散到不同 broker 以实现容灾隔离
- leader replica 和 follower replica: 分区通过多副本实现容灾, leader 负责处理该分区的生产者写入请求和消费者拉取请求, follower 负责拉取 leader 的日志, 数据同步, leader 故障时, 选举一个 follower 成为新的 leader
- consumer group: 消费者组是一组共享同一个 `group.id` 的 consumer 实例:
  - 一个分区可以提供给多个消费者组消费
  - 消费者组内的一个消费者可以消费多个分区
  - 一个分区在一个消费者组中只会分配给一个消费者, 即 "单个分区内按顺序拉取日志", 以保证单个分区内消息顺序消费

## Kafka 为什么快

1. 追加写日志
2. 使用 page cache: 生产者先写入到操作系统页缓存, 再由操作系统刷盘, 消费者拉取近期消息时, 也可能命中操作系统页缓存
3. 生产者批量发送, 消费者批量拉取
4. 零拷贝: 直接在内核态将文件数据传递给网卡, 避免用户态和内核态间的数据拷贝, TLS 场景下该零拷贝优化失效
5. 批量压缩和分区: 批量压缩降低网络带宽和存储占用, 多分区将负载分散到多个 broker 和消费者

## Kafka 推送模型

### 推送模型和拉取模型

- push 是 broker 主动推送, 可以通过 ack 和 prefetch 实现可靠性和流量控制
- pull 是消费者主动拉取, 适合消费者自己控制批量大小和节奏
- kafka 的普通消费者使用拉取模型, 客户端主动向 broker 拉取消息, 适合消费者自己控制批量大小和节奏
- kafka 的客户端通过 `poll()` 等 API 拉取数据, 如果 broker 暂时没有足够的数据, broker 可以等待到指定条件或超时再响应, 避免客户端重新发送空请求

### 消费进度

每个消费者组独立维护各个分区的已提交 offset

### 如何保证顺序拉取消息

- 一个分区在一个消费者组中只会分配给一个消费者, 即 "单个分区内按顺序拉取日志", 以保证单个分区内消息顺序消费
- kafka 不保证一个 topic 的所有分区的全局顺序

## 如何解决消息重复消费

### 案例

1. 生产者重试: 生产者发送消息到 broker, 但是 broker 返回的确认丢失, 导致生产者重新发送消息
2. 消费者重试: 消费者扣减库存, 但是还未提交消费进度就宕机了, 导致消息被重复投递, 消费者故障恢复后库存被扣减两次

### 幂等键, 条件更新和消息去重

1. 幂等键: 例如创建订单请求携带幂等键, 重复请求携带相同的幂等键, 数据库使用唯一约束, 第一次请求插入后, 重复请求不再重复插入
2. 条件更新: 例如支付服务发送的支付成功消息只能将订单服务的订单状态从未支付更新为已支付, sql 中包含订单状态条件判断, 第一次请求更新后, 重复请求不再重复更新
3. 消息去重: 订单服务收到消息后, 本地事务中原子执行消息去重和订单状态更新

## 如何保证消息队列的可靠性 (如何解决消息丢失)

1. 消息生产者同步发送时需要检查发送结果, 异步发送时需要处理成功和失败回调; 超时可能是发送失败, 或者发送成功但是确认丢失, 重试时需要使用幂等键
2. broker 需要有多副本和持久化
3. 消息消费者需要先处理业务, 再确认消费 (ack, 提交 offset); 如果业务处理失败则重试, 超过最大重试次数时加入死信队列并记录异常, 告警, 补偿

## 如何保证消息队列的顺序性

保证的是同一个业务键的局部顺序, 例如订单 a 先创建, 再付款, 最后完成; 这 3 条消息必须按顺序完成; 但是订单 a 和订单 b 通常无需相互排队

1. 生产者有序发送
2. 发送到同一个有序通道, 例如 kafka 的同一个分区
3. 消费者串行处理: 同一个业务键的消息串行处理, 不同业务键的消息可以并行处理
4. 消息处理失败时不能继续处理: 例如付款消息处理失败时, 不能继续处理完成消息更新业务状态, 而是阻塞该有序通道

## 如何保证幂等写

同一个业务操作执行一次和执行多次, 产生的副作用相同

1. 插入类业务, 使用幂等键和唯一约束
2. 状态流转类业务, 使用条件更新
3. 累加类业务, 使用业务流水消息去重

分布式锁解决的是同一时刻哪个实例可以执行, 分布式锁释放后重复消息仍然可以再次执行; 分布式锁不能代替幂等键

## 如何定位消息队列的消息积压

消息积压的本质是生产速度持续超过消费速度

1. 定位
   - 是所有队列都积压, 还是某一个队列积压
   - 生产量有没有突增, 消费者有没有掉线
   - 单条消息耗时, 失败率, 下游接口超时, 数据库慢查询
2. 优化 sql, 提高消费能力

## 本地消息表保证数据库和 MQ 的数据一致性

例如创建订单时, 同一个数据库事务中同时: 插入订单, 插入一条状态为等待发送的消息; 事务成功两条记录都存在, 事务失败两条记录都回滚

事务提交后, 后台线程定时扫描消息表中, 状态为等待发送的记录, 发送到 MQ

如果发送成功, 但是更新已发送状态时宕机, 后续扫描时会重新发送, 最终一致性还依赖下游消费的幂等, 顺序和对账

## 最多一次, 至少一次, 恰好一次

- 最多一次 (At Most Once): 消息最多投递 1 次, 最多处理 1 次, 但可能丢失消息
- 至少一次 (At Least Once): 消息可能投递多次, 可能处理多次, 但不会丢失消息
- 恰好一次 (Exactly Once): 处理结果只生效 1 次
