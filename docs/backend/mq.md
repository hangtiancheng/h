## 为什么需要消息队列

1. 解耦: 减少直接依赖
2. 异步: 缩短主流程响应时间
3. 削峰填谷: 缓冲突发流量

## Kafka

- topic: record 消息按 topic 主题分类, producer 生产者向指定 topic 生产消息, consumer 消费者从指定 topic 消费消息; topic 支持多订阅, 同一个 topic 可以被多个消费组消费
- partition: topic 拆为多个 partition 分区, 每个分区是一份追加 (append-only) 日志, 分区内的消息有 offset 偏移量, 分区是分布式日志的基本单位, 也是并行读写的基本单位
- broker: kafka 集群中的服务进程节点, 负责接收生产者写入请求, 持久化分区日志, 响应消费者拉取请求, 维护副本同步状态; 一个 broker 可以承载不同 topic, 不同分区的副本 (leader 副本或 follower 副本), 一个分区的多个副本尽量分散到不同 broker 以实现容灾隔离
- leader replica 和 follower replica: 分区通过多副本实现容灾, leader 负责处理该分区的生产者写入请求和消费者拉取请求, follower 负责拉取 leader 的日志, 数据同步, leader 故障时, 选举一个 follower 成为新的 leader
- consumer group: 消费者组是一组共享同一个 `group.ID` 的 consumer 实例:
  - 一个分区可以提供给多个消费者组消费
  - 消费者组内的一个消费者可以消费多个分区
  - 一个分区在一个消费者组中只会分配给一个消费者, 即 "单个分区内按顺序拉取日志", 即以保证分区内消息顺序消费

## Kafka 为什么快

1. 追加写日志
2. 使用 page cache: 生产者先写入到操作系统页缓存, 再由操作系统刷盘, 消费者拉取近期消息时, 也可能命中操作系统页缓存
3. 生产者批量发送, 消费者批量拉取
4. 零拷贝: 直接在内核态将文件数据传递给网卡, 避免用户态和内核态间的数据拷贝, TLS 场景下该零拷贝优化失效
5. 批量压缩和分区: 批量压缩降低网络带宽和存储占用, 多分区将负载分散到多个 broker 和消费者

## Kafka 推送和拉取

### 推送模型和拉取模型

- push 是 broker 主动推送, 可以通过 ack 和 prefetch 实现可靠性和流量控制
- pull 是消费者主动拉取, 适合消费者自己控制批量大小和节奏
- kafka 的普通消费者使用拉取模型, 客户端主动向 broker 拉取消息, 适合消费者自己控制批量大小和节奏
- kafka 的客户端通过 `poll()` 等 API 拉取数据, 如果 broker 暂时没有足够的数据, broker 可以等待到指定条件或超时再响应, 避免客户端重新发送空请求
